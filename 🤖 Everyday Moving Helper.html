👴 The Problem Worth Solving

Carrying loads is something most people take for granted — but for elderly individuals, parents pushing strollers, or anyone recovering from an injury, transporting groceries, laundry, or equipment across a building is a daily physical strain and safety risk. Falls caused by carrying heavy items are among the leading causes of injury in older adults.

ModuCargo started as a straightforward question: could a small, affordable robotic platform reduce that physical burden? Not a warehouse-scale AGV costing tens of thousands of dollars — but something built from hobbyist hardware that could navigate the same floors people actually live on.

How ModuCargo Works

The platform is built on the Cokoino CKK0015 4WD Mecanum chassis, controlled by a Raspberry Pi Pico running MicroPython. Two sensor systems run in parallel — a load cell that measures how much weight is on the deck, and an IMU that monitors tilt angle and terrain vibration. Every 250ms, a decision loop reads both sensors and adjusts motor speed accordingly.

Mecanum wheels were chosen specifically because they allow sideways movement without rotating the chassis. For a cargo platform following a person through a narrow hallway or doorway, this matters: the platform can slide into position without the load shifting.

Quantitative System Performance

Real-time analytical trends captured over 30-second test sweeps with a 500g payload.

Force Sensor Readings over Time (XFW-HX711)

Total measured weight in grams — 500g payload + ~448g platform = ~948g baseline. Spikes indicate dynamic impact loads from terrain.

Key Finding: Standard deviation scales 6.7× from smooth (±8.7g) to rough (±58.1g). The overload stop threshold of 1050g was breached on rough terrain approximately 18% of the time — consistent with the wheel-impact model. On smooth and carpet surfaces, the threshold was never reached under a 500g payload.

Platform Tilt Angle over Time (MPU6050)

Tilt angle in degrees derived from accelerometer. The red dashed line marks the 15° safety stop threshold.

Key Finding: Rough terrain produced a tilt spike of 19.32° — 4.32° above the stop threshold. Carpet peaked at 8.58°, comfortably within the caution zone but not triggering a stop. This confirms the terrain classification is meaningful: the same sensor produces qualitatively different behaviour on each surface type.

Sensor Noise Comparison — Standard Deviation by Surface

How much each sensor varies across the three surfaces. Higher variance = noisier signal = harder terrain. All three sensors scale consistently.

Key Finding: All three sensors scale in the same direction — confirming they are independently detecting the same physical phenomenon. Gyroscope noise is the most sensitive indicator (9.9× increase from smooth to rough vs. 6.7× for force and 4.5× for tilt), making it the best candidate for early terrain detection before dangerous conditions develop.

Engineering Challenges

What was hard — and how we resolved the gap between wiring a component and extracting reliable biological/hardware data.

01
Distinguishing Terrain Impact Spikes from Overload
The Problem

A mecanum wheel hitting a floor seam or small obstacle causes a momentary 100–120g spike on the force sensor — identical in magnitude to a genuine cargo overload. A naive threshold check would trigger a false stop every time the platform crossed a tile joint, making it unusable on anything but perfectly smooth floors.

The Solution

Replaced single-sample threshold checks with a rolling 5-sample window average. The overload stop only triggers when the mean of the last five readings exceeds 1050g — roughly 1.25 seconds of sustained overload. Momentary spikes average out and do not trigger the stop. This was validated against the rough terrain dataset, where 18% of individual samples exceeded 1050g but no 5-sample window mean did.

02
MPU6050 Silent Data Corruption from Incorrect Supply Voltage
The Problem

The MPU6050 is a 3.3V device. Connecting its VCC to the Pico's VBUS (5V) doesn't destroy the sensor — it appears to function, the I2C bus is acknowledged, and readings come back. But the values are silently corrupted: accelerometer outputs were stuck near ±2g regardless of orientation, and gyroscope readings showed constant DC offset drift. There was no error flag and no obvious visual indication.

The Solution

Identified by comparing expected gravity vector magnitude (should read exactly 1.0g on the Z-axis when flat) against actual readings. When the magnitude deviated by more than 15%, voltage rails were inspected. Rewiring VCC to the Pico's 3.3V output pin immediately produced correct readings. Added a startup self-check to the firmware that reads the Z-axis accel, computes the magnitude, and halts with an error if it falls outside 0.90–1.10g.

03
Mecanum Wheel Orientation Causing Unintended Diagonal Drift
The Problem

Mecanum wheels must be arranged so their 45° rollers form an X pattern when viewed from above — two wheels with rollers angled one way, two angled the opposite way. A single incorrectly mounted wheel causes the platform to drift diagonally during any commanded movement. This is not immediately obvious because the platform still moves in roughly the right direction — it just drifts 15–20° off axis, which only becomes apparent over a longer run.

The Solution

Diagnosed by running each motor pair independently and observing the resulting chassis movement. Correct front-left + rear-right pairing should produce a pure lateral slide — if it produced rotation instead, a wheel was misoriented. After remounting the front-right wheel (roller angle was mirrored), all four movement directions — forward, backward, strafe left, strafe right — produced clean straight-line motion without drift. Assembly notes now include an explicit roller-angle diagram for each wheel position.

04
HX711 Zero-Point Drift Across Power Cycles
The Problem

The load cell requires calibration against a known weight to convert raw ADC counts into grams. Without storing this calibration value, every power cycle produced a different zero-point offset — readings drifted by ±30g between sessions. This was large enough to produce false overload warnings on carpet even with no payload, making the system unreliable across sessions.

The Solution

Calibration data (zero offset and scale factor) is now written to the Pico's onboard flash memory after each calibration run using MicroPython's uos and file I/O. On boot, the firmware reads the stored values before taking any sensor readings. A re-calibration flag can be triggered by holding a GPIO pin low during startup, prompting a new calibration sequence. After this fix, zero-point consistency across 20 power cycles was within ±4g.

Technical Stack

Pristine coordination between rapid microcontrollers, physical drivers, and statistical processing.

Raspberry Pi Pico

Main controller — RP2040 dual-core running MicroPython. Chosen over Arduino for native file operations and scalable Python library support.

L298N Motor Shield

Dual H-Bridge driver regulating 4x DC motors. Dynamic pulse-width modulation (PWM) scales speed variables between 0-100%.

XFW-HX711 + 3921 Load Cell

24-bit analog-to-digital converter reading high-accuracy strain-gauge deck weights. Calibrates values natively on boot.

MPU6050 IMU

6-axis accelerometer & gyroscope mapping motion. Uses a strict 3.3V power routing layout with startup gravity vector validation checks.
